7. Firmware System Architecture

This section documents the firmware architecture from sensing to estimation, control allocation, actuator interfacing, and output safety limiting. The structure is written as implementation-oriented documentation to support tuning, debugging, and future maintenance.

7.1 System Structure

The firmware is organized as a fixed sequence: \[ \text{Acquire} \rightarrow \text{Estimate} \rightarrow \text{Control} \rightarrow \text{Map/Limit} \rightarrow \text{Actuate}. \] The design objective is to keep signal validity and sign consistency before control commands are issued.

Table 7.1. Firmware layer structure and main outputs.

Layer Function Typical outputs
Acquisition IMU, encoder, and motor data reading with freshness checks. \(pitch,\ \dot{pitch},\ rpm,\ encoder\ angle\)
Estimation Bias-corrected attitude and translational state reconstruction. \(x,\dot{x},\theta,\dot{\theta},\phi,\dot{\phi}\)
Control LQR/VMC/PD calculations in model-consistent coordinates. \(u=[T,\ T_p]^T\)
Mapping + Safety Driver command mapping, saturation, rate limiting, and safety lock checks. Safe actuator command packets

Reference code: firmware_system_structure.c

7.2 Acquisition of Sensory Data (IMU + Kalman Filter)

Purpose in this project

This stage combines raw onboard sensing (IMU + encoder/motor data) with filtered state estimation, so the controller receives stable and usable states. The IMU supplies fast attitude-rate information, while the estimator reduces noise and drift before the LQR/VMC stack uses the data in imu_processing_pipeline.c and kalman_body_state_estimator.c (Kalman, 1960).

IMU processing role

  • Reads raw gyroscope and accelerometer channels each control cycle in imu_processing_pipeline.c.
  • Applies startup bias compensation and runtime filtering to reduce sensor noise in imu_processing_pipeline.c.
  • Enforces sign-convention mapping so firmware pitch channels remain consistent with the model state definition in sign_convention_alignment_check.c.
  • Provides reliable short-horizon tilt and angular-rate cues for balance correction in imu_processing_pipeline.c.

Kalman-filter role in the same pipeline

The estimator uses a recursive prediction-update structure from linear state-estimation theory to keep controller states smooth and usable in runtime (Kalman, 1960).

  • Combines multiple noisy measurements into a smoother translational/body-state estimate in kalman_body_state_estimator.c.
  • Improves state continuity during encoder jitter and short bursts of IMU disturbance in kalman_body_state_estimator.c.
  • Produces controller-ready estimates for \(x,\dot{x},\theta,\dot{\theta},\phi,\dot{\phi}\) in kalman_body_state_estimator.c.
7.3 HT8108 joint motor control interface (Joint Motors)

The HT8108 interface performs command packing, communication transmission, and status monitoring for joint channels. Commands are converted from physical units into protocol-specific packed integers with strict min/max clamping.

Practical issues encountered during integration include sign mismatch, parameter-limit clipping, and communication timeout handling. So the interface includes both command validation and readback checks before enabling high-level control.

Sample control code (HT8108 command pack and send)

#include <stdint.h>

void ht8108_pack_and_send(float p, float v, float kp, float kd, float t, int motor_id)
{
    // Apply command limits and pack frame fields.
    (void)p; (void)v; (void)kp; (void)kd; (void)t; (void)motor_id;
    // Transmit command over CAN.
}

Sample readiness check (sign consistency + driver status)

#include <stdbool.h>

typedef struct {
    float test_cmd;
    float measured_speed;
    bool drv_ok;
} motor_diag_t;

static bool sign_match(float cmd, float speed)
{
    if (cmd > 0.0f && speed < 0.0f) return false;
    if (cmd < 0.0f && speed > 0.0f) return false;
    return true;
}

bool actuator_ready_check(const motor_diag_t *m)
{
    if (!m->drv_ok) return false;
    if (!sign_match(m->test_cmd, m->measured_speed)) return false;
    return true;
}
7.4 M3508 wheel motor control interface (Wheel Motors)

The M3508 interface maps generalized wheel-channel commands to left/right motors and reconstructs wheel speed/position from encoder telemetry for estimation and feedback closure.

Sample control code (M3508 speed mapping and wheel-center speed)

#include <stdint.h>

typedef struct {
    int16_t rpm;
} m3508_raw_t;

float m3508_speed_mps(const m3508_raw_t *m, float rpm_to_mps, int sign)
{
    return sign * m->rpm * rpm_to_mps;
}

float wheel_center_speed(float vL, float vR)
{
    return 0.5f * (vL + vR);
}
7.5 Torque command saturation and output limiting

Output limiting is implemented to ensure motor commands remain within electrical, thermal, and stability-safe envelopes. Hard magnitude clipping and optional slew-rate limits are applied before command transmission.

\[ u_i^{sat}=\mathrm{clip}(u_i,\,-u_{i,\max},\,u_{i,\max}), \qquad \dot{u}_i^{sat}=\mathrm{clip}\!\left(\frac{u_i(k)-u_i(k-1)}{T_s},-\dot{u}_{i,\max},\dot{u}_{i,\max}\right). \]

For this project, the torque clipping is applied per actuator group as follows.

Channel Clipped Command Clip Limit Used
M3508 wheel motor (left) \(T_{w,L}\) \(\left|T_{w,L}\right|\le 3\ \mathrm{Nm}\)
M3508 wheel motor (right) \(T_{w,R}\) \(\left|T_{w,R}\right|\le 3\ \mathrm{Nm}\)
HT8108 joint motors (4 channels) \(T_{j,i},\ i\in\{1,2,3,4\}\) \(\left|T_{j,i}\right|\le 6\ \mathrm{Nm}\) motor-side (\(\approx 36\ \mathrm{Nm}\) after \(1{:}6\) reduction)

Any command exceeding these limits is clipped before transmission, and the same channel also passes through the rate limiter \(\dot{u}_{i,\max}\) to avoid sudden torque jumps.

Over-tilt cut-off is treated as a high-priority safety lock: if \(|pitch|>pitch_{lim}\), torque output is forced to zero.

Reference codes: torque_saturation_output_limit.c, over_tilt_safety_cutoff.c
